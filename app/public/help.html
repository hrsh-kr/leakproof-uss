Help and rules

This page is plain text and needs no login and no extra software. The full guide is USER_GUIDE.md in the submission package.

What LeakProof is

LeakProof runs one exam so that no single person can read the paper early, and a leaked copy points to a seat. Questions are encrypted as TAs submit them. At sealing, one question per topic is drawn and the paper is locked under a key held by the professor (1 key card). The professor must approve before the paper opens. Each seat then gets the same questions in its own order, so a leaked copy can be traced to a seat, not to a person.

How to start (practice instance)

Practice address: https://192.168.2.238:8443/. Demo pods (shared accounts, listed in TESTERS.md): https://192.168.2.238:7443/.

  1. Open the app, choose Join a class and enter the course code for your role — LP-PROF-G19 (professor), LP-TA-G19 (TA), or LP-STU-G19 (student) — a username (3 to 32 characters: lowercase letters, digits, dot, dash or underscore), and a display name.
  2. You see a passphrase and a recovery code once. Press Copy both or Download, tick the box, then Continue.
  3. In the practice instance you can register accounts for all three roles: TA, professor (key holder), and student. Follow the Next step box on the exam page.
  4. The browser warns about the certificate because it is self-signed. This is expected. Press Advanced and then proceed (Chrome and Edge), Accept the Risk and Continue (Firefox) or visit this website (Safari). To check the root certificate, compare its SHA-256 fingerprint with the one in TESTERS.md; the steps are in section 2 of the user guide.

The practice instance has no shared accounts: register your own. The demo pods have shared accounts on the honour system, restored every night. This page shows no passwords.

The three stages

  1. Collect. TAs add one question per topic. Every topic needs at least 1 question from a TA before sealing.
  2. Seal. The professor presses Seal the exam. One question per topic is drawn, the paper is locked, 1 key card is issued to the professor, and every other question is deleted. The professor creates the card with a passphrase of at least 14 characters, saves the file and verifies it. The server then deletes its own copy. The card must be verified before release can be requested.
  3. Release. Inside the print window the professor enters the number of seats and presses Request release. Two words appear on their screen. The professor types the words, loads their card, types its passphrase and presses Approve with card 1. The paper opens and each seat can be printed. The first print of a seat is logged; reprints are counted. The request expires after 15 minutes.

Rules for testers

In scope

  • The practice instance and the demo pods, from a browser or curl, with accounts you registered yourself or the demo accounts.
  • The source tarball run locally, for code review.
  • Functional bugs: anything that does not match the user guide.

Out of scope

  • Any DDoS or flood, from one machine or many. This is not allowed.
  • The host machine, its operating system, SSH and the proxy admin port.
  • The official instance (it runs on the night of 25 Nov and is not open to testers), other groups' systems, social engineering, physical access.

Please keep it low volume

A few hundred requests per test is plenty. Do not create accounts in bulk; the daily sign-up cap applies.

Known limits

  • The server operator can read memory while the paper is open. A trusted operator is assumed; see SECURITY.md.
  • The certificate is self-signed, so the browser warns once.
  • The two-word check is a presence check with 5 tries per key holder and request, not strong cryptography.
  • The professor can veto a release by refusing it; the log shows it.
  • A trace names a seat, not a person. It needs the questions with their options to name a single seat.
  • In the practice instance you can register one account per role to try the full pipeline.
  • Rate limits apply per network and per account.
  • Full list: section 12 of the user guide and SECURITY.md section 4.

Works as designed

Please do not report these as bugs.

  • A refusal closes the release request. The professor can request release again.
  • A verified card cannot be shown again. Keep the file and its passphrase.
  • A server restart locks the paper again and closes open requests.
  • You are signed out after 30 minutes without activity.
  • A missing role answers "Not found", the same as a missing exam.
  • There are no email or SMS codes. The recovery code is the way back in.
  • Usernames are unique, so sign-up says when a name is taken.
  • Five wrong tries of the two words lock the professor out of that request. A new release request is needed.
  • A trace needs the questions with their options to name a single seat.
  • The answer key is per seat: each seat has its own question order.
  • Demo pods are restored every night at 04:00 server time. Sessions end and open papers lock again.

How to report

Send the steps, the exact request and response, what you gained, and whether it works on a fresh account. Say which instance, account and browser you used. Tell the team before filing that the site is down. How to reach us: see TESTERS.md. This does not replace your own official submission.
