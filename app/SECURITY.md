# LeakProof: security requirements, measures and proof

Every claim in sections 1 and 2 has a test in `tests/` (run `npm test`); tests are cited by the start of their title. Measures that no automated test can reach
(the browser's card encryption, Caddy, the firewall, systemd) are listed separately in section 5, with how each is checked.

## 2. Lessons from FCS Group 1 and Group 2

Source: `../reference/fcs/fcs_bugs.csv` (bugs validated by the course staff). Group 1 had 13 valid reports out of 72, Group 2 had 1 out of 45.

| Valid bug (group) | Class | What we did | Test |
|---|---|---|---|
| Accounts created with no verification; bot sign-ups (G1, 4 reports) | Authentication / abuse | Practice registration needs the course code from the guide; at most 30 successful sign-ups per client per day (failed attempts do not count, so a shared hostel or lab address is not locked out) and 2000 accounts in total; official accounts are pre-created only; no email is used, so no one can squat someone else's address | `FCS-G1 no unverified mass sign-up…`, `S8 shared networks…` |
| No forgot-password path (G1) | Availability of the account | A one-time recovery code is shown with the passphrase; using it sets a new passphrase and signs out every session; the code works once even if two requests race | `FCS-G1 no forgotten-passphrase…`, `S16 recovery codes are single-use…` |
| Search endpoint leaked every user's id, email and role (G1) | Information disclosure | No user list or search exists; responses are built from explicit fields; the public log has no names | `FCS-G1 no user directory…`, `SR6 the log head…` |
| No limit on API requests; brute force possible (G1) | Missing rate limit | Every API route is rate-limited per client (429 with the real `Retry-After`, not 503 as G2 did); login, register, recover share a 30/min bucket; the public check-head has its own | `FCS-G1/G2 rate limits…`, `S8 shared networks…`, `S16 Retry-After…` |
| TCP connection flood took the site down (G1 and G2) | Denial of service | Slow-header timeout checked every second; short keep-alive; password hashing off the main thread; a per-client socket cap in the app for direct runs (behind Caddy, the firewall's `connlimit` and Caddy's timeouts do this, see section 5); the public log returns at most 200 entries and re-verifies the chain (a full walk) at most every 30 s; log growth is capped: one row per card fetch, three per seat reprint | `FCS-G1/G2 connection flood…`, `FCS-G1/G2 a login flood…`, `S3 the public log returns…`, `R5-S2 a seat can be reprinted…` |
| "End-to-end encrypted" chat was not (G1, 3 reports) | Over-claiming | Every claim in sections 1 and 2 has a test; what is checked another way is in section 5; limits are in section 4 | this file |
| Profile photo upload did not display (G1, 3 reports) | Broken feature | No uploads at all; the whole pipeline runs end to end over real HTTP in the tests | golden path |

Invalid reports against both groups still show what classmates try first: XSS in names, CSRF on logout, IDOR on ids, path traversal, session reuse after logout, lockout abuse. Each has a test above.

## 3. What we took from their designs, and what we cut

Kept (cheap, and each removes a class of bug): Group 2's proxy timeouts, body cap and TLS-only front end, blocking of `.env`/`.git` paths, `SameSite=Strict` cookies, dummy hash on unknown users, sessions killed after a credential reset, a confirmation step before sealing, per-action daily caps, a health check after deploy; Group 1's double-submit idea (as a session-bound CSRF token), trusting `X-Real-IP` only from the proxy, a key cap on the in-memory rate limiter, hiding the server banner, systemd service, and a post-deploy smoke script (ours asserts exact statuses and headers).

Cut (no property is lost for this system): TOTP and the virtual keyboard (the high-risk action, approving a release, already needs a card plus its passphrase plus the two words), JWTs (server-side sessions are simpler to revoke), IP-bound sessions (break on mobile networks), file uploads and PKI-signed files (we accept no files), HTTP/2 at the proxy (removes the Rapid Reset class tried on G1), an automatic restart on failed health checks (a restart re-locks the paper mid-exam), React and every npm dependency (zero dependencies means no supply-chain or known-CVE surface).

Avoided their mistakes: Group 1 committed its TLS private key and a database dump, and regenerated its keys silently; here `data/`, `*.key` and `*.db` are git-ignored, keys are generated on the server at install time, and the server will not start with a missing key over existing data. Group 2's provisioning left the operator with working credentials for every account; ours must be replaced at first login.

## 4. Limits we state openly

- The server process handles the plaintext paper for milliseconds at sealing and while it is open after release. The exam cell sees the paper when it prints. A malicious VM operator could serve altered JavaScript.
- The professor holds the single key card and can open the paper; the log shows it.
- **The professor can veto a release.** A refusal (which needs the two words from the exam cell screen) closes the request. We chose fail-safe: a professor who sees something wrong must be able to stop printing. The exam cell can request again, and every refusal is logged.
- Until the card is verified, the server holds that share (wrapped under its own key): the gate is enforced by software until then. After verification the cryptography protects the paper against someone who steals the database and keys; it does not protect it from the running server while the paper is open.
- **The professor's card plus a copy of the database can open the paper offline.** The encrypted paper is in the database; one card reconstructs the key. The log would not show that. This is the threshold working as designed, not a bug.
- **The operator can grind the draw seed.** The server picks the seed, so a malicious operator could seal repeatedly and keep the draw they like. The seal log entry commits to sha256(seed) before it is revealed, so the seed cannot be changed after sealing; it does not prove the operator did not choose it.
- **The copy id is not verified by the server.** It is printed on each copy and re-derivable by the exam cell; there is no route that accepts a copy id and checks it.
- **The setter's id stays in the database for drawn questions** (`questions.setter_id`, with the ciphertext deleted). The public log and every API response omit it.
- A trace can match several seats when the pasted fragment has no options (or too few questions); the result then says how many and asks for the options.
- The operator who runs `official-setup.mjs` sees each printed passphrase and could log in before its owner. The owner would notice: their printed passphrase no longer works, and the change is in the log.
- **Registration says whether a username is taken** (409). Usernames are not secret here: there is no directory, no email, and every passphrase is generated (80 bits).
- The print window and seat count are set by the exam cell; they guard against accidents, not a malicious exam cell.
- A trace names a seat, not a person, and works on text that preserves the question and option order (copy-paste or a careful transcription), not on a blurred photo.
- A photo of a printed copy cannot be prevented, only traced. The log shows tampering; it does not prevent it.
- After a restart the paper locks again and the professor must approve again; a request in progress becomes `interrupted` (by design: the open paper and the approval share exist only in memory).
- The two-word check has 14 bits; with 5 tries the chance of guessing the right words is about 5 in 16,384, and every wrong try is logged. The professor locked out of a request stays locked out of it; the exam cell requests release again (new words).
- A `server.key` restored from the wrong backup is not detected at start-up: the service runs and `/healthz` is green, but stored questions and key-card shares cannot be opened. The operator keeps keys with the data (`deploy/backup.sh`) and checks one sealed exam after any restore.
- Volumetric DoS from many machines, compromise of the VM host, and social engineering are out of scope.

## 5. Measures checked outside `npm test`

| Measure | Where | How it is checked |
|---|---|---|
| Key card encrypted in the browser under the holder's passphrase (PBKDF2 600k + AES-GCM, AAD exam\|slot) | `public/app.js` | By hand in a browser; the server-side half (verify-on-claim) is tested |
| Unknown usernames pay for a dummy scrypt hash, so timing does not reveal them | `src/crypto.mjs` `burnPasswordTime` | Code review; the identical message is tested, the timing is not |
| Caddy: TLS (internal CA, fingerprint published), HTTP/1.1 only, header/body/idle timeouts, 32 KB body cap, no `Server` header, `X-Real-IP` set by the proxy; request-rate limits are the app's own (tested above) | `deploy/Caddyfile` | `deploy/smoke.sh https://<vm>:8443` after each deploy |
| Firewall: default deny inbound except 22, 8443, 9443; `connlimit` 50 per address; re-applied by systemd at every start | `deploy/firewall.sh`, `deploy/leakproof@.service` | `smoke.sh` (Node ports closed from outside); `iptables -S` on the VM |
| systemd sandbox: own user, read-only system and keys, `MemoryMax`, `Restart=always` | `deploy/leakproof@.service` | `systemd-analyze security leakproof@practice` on the VM |
| Deploy gate: `install.sh` runs `npm test` first and a health check last; self-signed certificate carries a SAN | `deploy/install.sh` | Output of the install run |
