# S3 round 3: requirements and threat model

**1. Biggest hole.** One process, one SQLite, one key file and one log hold the official exam and 80 practice exams, and the tester passwords are public. A classmate logs in as `tester03`, then floods wrong passwords at the official Dean and Registrar accounts. Per-account backoff locks them out and the 26 Nov demo dies. One IDOR on `/releases/:id` would also reach the official exam. Every practice click lands in the same hash chain, so "head hash after each stage" means nothing, and `reset-tester N` cannot delete rows without breaking the chain.

**2. SR1-SR12 after the cuts**

| SR | Status |
|---|---|
| 1 | Holds. "Role" becomes "capability". Add an object-level test (other exam's IDs, random IDs); a route x capability matrix misses IDOR. |
| 2 | Holds. Cap backoff at 30 s, no lockout; per-IP limit high (campus NAT). Tester passwords are public by design, so "I logged in as tester07" is not a finding; say so in the guide. |
| 3 | Reword: the exam cell sees counts until release, and the paper at print. |
| 4 | **False for practice**: one account holds five slots. Reword: "a slot approves once; an account approves only slots assigned to it; on the official exam, one slot per account." No `practice` flag in code; derive it from assignments. Before a card is claimed, the share sits on the server behind a login password only, so release needs 5/5 claimed. |
| 5 | Reword (centre becomes exam, seating becomes seat count). G2 and G3 are parameters the exam cell sets itself. They stop mistakes and replay, not a malicious cell. Freeze both at Seal, log them, show them on the key holder's approve screen. Only G1 is independent. |
| 6 | **Broken.** Doc 11 dropped the keyed chain and the second anchor. Anyone with DB write recomputes the whole chain, and truncation passes. Restore the HMAC key and post the head after Seal and Release elsewhere. Claim: "detected by anyone holding an earlier head." |
| 7 | Holds. State what trace keeps after close, and that pre-claim shares are wrapped. |
| 8 | A seed hash logged at Seal commits to nothing; the operator can grind. Generate the seed at exam creation and log its hash then (free), or drop "committed". |
| 9 | Holds. The copies arrive as one HTML response, so "every print is logged and capped" is false. Say "issued once, re-issues logged". |
| 10 | The public log shows 80 testers' free text (exam titles, names): defacement and fake-looking log lines. Log enum codes and IDs only. |
| 11 | Holds. Official passwords must be generated on the VM, never in the seed script or package. |
| 12 | "Human confirms" is hollow when the printer also traces. Reword: lead with scores, no accuse action, queries logged. |

**3. Cut too far.** (a) A seal precondition: topics fixed at exam creation, at least 2 distinct setters per topic. Without setter assignments and with free-text topics, a setter invents a topic and is guaranteed into the paper, which loses P2. (b) The keyed chain and anchor (SR6).

**4. Not cut far enough.** `POST /exams` on practice builds: pre-create practice exams, so nobody can mint exams or assign capabilities.

**5. Honest claims, rewritten.** "No single account can read the paper before release unless it controls the server. The exam cell sees it only after three key holders approve. The server operator, or three colluding key holders, can open it early. The log exposes edits to anyone who saved an earlier head hash. A trace names a seat, not a person, and is a lead. Practice exams give one account all five cards on purpose; the three-person rule is shown on the official exam."

**Verdict: ACCEPT WITH CHANGES.** Ranked:
1. Official instance separate (own port, DB, key, chain); resets create a new exam ID (0.3 d)
2. Keyed log plus external head (0.2 d)
3. Per-slot rule, frozen window and limit shown to key holders, SR rewordings (0.3 d)
4. Seal precondition on topics and setters (0.15 d)
5. Object-level tests, enum-only log (0.2 d)
6. Backoff cap (0.05 d)
