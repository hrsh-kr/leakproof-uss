# R5: Group 2 (VajraKavach) usability and usable-security catalogue (H1/U1 lens)

Role-played lens for a student project, not the views of a real person. Research only: no code was changed, and no Group 2 script was run.

**Paths.** `G2/` = `/private/tmp/claude-501/-Users-hrshkr-Downloads-sem8-uss/29dd3dd2-a7a9-4bdd-b465-6e19cbfa674a/scratchpad/g2/VajraKavach-main/`; `FE/` = `G2/frontend/src/`; `BE/` = `G2/backend/app/`. Ours: `app/` = `/Users/hrshkr/Downloads/sem8/uss/project/app/`. CSV rows are numbered as Python's `csv` module parses `fcs/fcs_bugs.csv` (header excluded, 1-based). Group 2 has rows 73 to 117.

**Users we filter for.** S = setter, C = exam cell (`run`/`print`), K = key holder, T = lone practice tester (plays every role, 18 to 25 Nov).

**What Group 2 is, as far as UX goes.** A React and Tailwind SPA of 16 pages (`FE/App.jsx:56-75`). Its usable-security work centres on TOTP: a QR code at registration, TOTP after every login, and fresh TOTP through a shuffled on-screen keypad for risky actions. Around that sit role dashboards, field-level privacy selects, a "Danger Zone" with a typed phrase, and a global rate-limit toast. Most of the polish is visual. Accessibility work is thin, and step-up is applied unevenly (several places fall back to `window.prompt`).

## 2. Usability complaints classmates raised against Group 2, and the lesson

Staff marked 44 of 45 Group 2 rows Invalid; the only Valid one was a socket-flood DoS (row 116). Many Invalid rows were still real **user-experience** signals. Testers file confusion as bugs.

| Row | Complaint (gist) | Ruling and rebuttal | Lesson for LeakProof |
|---|---|---|---|
| 73 | Password checklist "helps attackers craft inputs" | Invalid; "a feature not a bug" | Showing the rules is fine. We have no composition rules anyway (server-generated login passphrase) |
| 74 | Different behaviour for unknown email vs wrong password | Invalid (tester typed a non-email) | Keep one message for both: ours says "Username or passphrase is wrong." (`app/src/app.mjs:150`) |
| 76 | One mistyped password leads to lockout | Invalid; "use Forgot password" | Lockouts must forgive honest typos and say how long to wait. Ours: 5 free tries, then 1 s doubling up to 15 min, keyed on username plus IP, with seconds shown (`app.mjs:84-94`) |
| 77 | "Poor UX: increases invalid submissions" | Invalid; "neither functionality nor security" | Vague UX reports get dismissed. Still, we should show limits up front (hints and counters) |
| 78 | "No OTP came to my email" | Invalid; "TOTP by design, in user guide" | **Testers don't read the design rationale.** Put "works as designed" items where testers look (guide section 3 and on-screen) |
| 79 | Eye icon enables shoulder surfing | Invalid; "standard practice" | Context decides. Our approval happens in a shared room, so no reveal toggle on approval |
| 81 | Name length limit too small | Invalid (1 to 255) | State limits in the hint text, and make the hint match the server (ours does not, see ADOPT 5) |
| 83 | "Weekly limit reached (5/week)" on the **first** registration attempt; a friend also blocked | Invalid after a bitter exchange; per-IP limit from a shared network | **The biggest UX lesson.** Per-IP quotas punish everyone behind one NAT, and testers treat that as DoS. Our `registerPerIp` is 5/day (`app/src/config.mjs:24`) and auth is 10/min per IP (`config.mjs:23`, `app/deploy/nginx.conf:5,47`). The kick-off on 18 Nov will likely have many testers on campus Wi-Fi |
| 84, 85 | "QR shown immediately with no email verification", so anyone can claim an email | Invalid; "instructor said no email" | Pre-empt: our practice accounts are bound to a username plus a course code, not an identity. Say so in the guide. The passphrase shown once at sign-up will draw the same "secret shown on screen" report |
| 86 | Incomplete applications reach recruiters | Invalid (screenshot from the wrong group) | n/a |
| 87 | Duplicate job postings allowed | Invalid; "product choice" | Ours: one question per topic per setter is enforced (design §3). Say so in the UI hint (we do, `app/public/app.js:332`) |
| 88 | "TOTP step reached without validating first factor" (it was the registration flow) | Invalid; "setup, not authentication" | Name each step clearly ("Step 1 of 2", which we do at `app.js:357,382`) so testers can tell setup from authentication |
| 89, 91 | "Site is down" (they were rate-limited; nginx answered 503 or refused) | Invalid; long rebuttal | A throttle must **look like a throttle**: a 429 with a readable sentence. We fixed the status (`nginx.conf:7`), but the nginx 429 body is HTML, so our client shows "Something went wrong." (`app.js:47-50`). See ADOPT 1 |
| 92 | IP-keyed TOTP lockout can be bypassed by rotating IPs | Invalid; team conceded per-account lockout would help | Key backoff on the account as well as the IP. Ours keys on `username|ip` (`app.mjs:146`). Fine for practice |
| 95, 96, 101, 113 | Self-registered "Admin" sees all users and resumes | Invalid; "read-only admin by instructor request" | Do not let self-registration choose a privileged role. Ours: each tester gets a private sandbox exam (`app.mjs:161-178`) |
| 97 | TOTP-only password reset means takeover if the seed leaks | Invalid; "documented trade-off" | Our recovery code is the analogous single factor. State it in SECURITY.md (it is a known limit) |
| 99, 102, 115 | Can apply without a resume; "UI does not say it is optional" | Invalid; "guide never says required" | Mark required/optional fields explicitly. Testers read silence as a bug |
| 103, 106 | Profile defaults to Public; privacy not enforced at API | Invalid | n/a (no profiles). Our analog, SR3 counts-only, is stated on screen (`app.js:239`) |
| 108 | Own IP shown in the UI and API is a "privacy leak" | Invalid; "documented session binding" | Do not show data with no task value; it only creates attack surface for reports |
| 110 | Rate limit returns 503 not 429 | Invalid, but the team agreed it should be 429 | Already fixed (`nginx.conf:7`) |
| 111 | Malicious page logs the user out (CSRF on logout) | Invalid (SameSite=Strict) | Ours: Origin check plus CSRF token on every non-GET (`app.mjs:269-276`) |

**Meta-lessons.**
- Testers file *confusion* as *bugs*. Each deliberate choice not explained on screen or in the guide costs a rebuttal.
- G2's rebuttals sometimes attacked the tester ("Prima facie... malicious and false", row 83; "read user guide" in capitals, row 84), which escalated the disputes. Rebut with evidence and keep it civil.
- Shared-network limits are the most likely way our own practice instance will look broken on 18 Nov.

## 3. Fit verdict for LeakProof

Principles used: friction in proportion to irreversibility; honest, computed indicators; recognition over recall; error messages that name cause, actor and next step (our G-gate rule); fail-safe defaults; no security feature without a user it protects (Occam).

## 4. Ranked ADOPT/ADAPT list (most valuable first)

1. **Shared-network limits** (row 83 lesson). Raise `LP_REGISTER_PER_IP` to about 30/day and `LP_AUTH_PER_MIN` plus nginx `lp_auth` to about 30/min. Per-username backoff and the 300-account cap remain the brakes. Otherwise the 18 Nov kick-off on campus Wi-Fi looks like an outage.
2. **Readable nginx 429** (rows 89, 91, 110). The client falls back to "Too many requests from this network. Wait a minute and try again." when the 429 body is not JSON (`app.js:47-50`); optionally add a JSON `error_page 429` in nginx.
3. **Key holder live refresh.** Poll `/api/me` every 10 s on Home and on Key cards while no request is pending, so "Waiting for you" appears without a reload (design §2 #14 is only half built).
4. **Session-end message and return path.** After the 30-min idle 401, show why and return to the same hash after login.
5. **One timezone.** Server `fmt` and client `when()` both in IST with a suffix, and show "Server time now" beside the print window.
6. **Log head on the approval screen.** It is promised in SR6 and design §2 #6; the server already sends `rel.head`.
7. **No swallowed release fetch** (`app.js:341`): show an error line instead of an empty screen.
8. **Seal confirm focus on Cancel** (`app.js:238`), and an in-place confirm for setter Delete (`app.js:316`).
9. **"Works as designed" list in USER_GUIDE §3.** It pre-empts G2's most common class of disputed reports.
10. **Small aids.** Question/option character counters; live card-passphrase length counter and mismatch hint; "Working…" label during PBKDF2; "bring this card to the release" line; username hint aligned with the server rule (`app.js:140` says "lowercase letters or digits", but the server also allows dot, dash and underscore, `app.mjs:164`).

**Rejected (Occam):** virtual keypad, TOTP/QR, composition-rule strength bar, reveal toggle on approval, auto-retry of POSTs, WebSocket, privacy selects, report button, pagination, decorative "Encrypted"/status badges, live IP display.
