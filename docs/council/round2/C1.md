# Q3, Advocate C1 (H1 + S3): offline shares, request-bound approval

## (a) Strongest case
- **Where a share lives decides who can read it.** A share held by the custodian (wrapped under their own passphrase, in their browser or a file) leaves the server holding nothing that opens the paper. A DB dump, backup or SQLi gives an attacker hashes and public keys only.
- **Approval must be an object the server can verify.** A UI click is not evidence. A signed, single-use, expiring request (exam, centre, nonce, expiry, two-word check) gives the log a record that custodian X approved request R.
- **Tired officials fail on typing and on rubber-stamping, not on cryptography.** One card, a two-word check, no typed pieces, and a separate "Something is wrong" path for the 4-of-5 fallback match H1's non-negotiables and S3's SR4/SR5.

## (b) Two best attacks on C2 (P2 + D2)
1. **The wrap key is not independent of the login password.** P2 derives it with scrypt from the password, and the server verifies that same password at login. The server sees the password in RAM, so it can unwrap that custodian's share. A classmate with DB read (D2 snapshots hourly to a second location) also gets all five blobs. Demo passwords are weak, so offline guessing opens three shares with no audit entry. This breaks SR4 and SR7. Also, P2 refuses to build password reset, so a forgotten password destroys a share for good.
2. **Submitting a share is not an approval.** The share is static and bound to no request. A sniffed submission (D2 allows plain HTTP as option iii) or a stolen session cookie replays forever, and the server cannot tell "custodian approved this release" from "someone holds the bytes". D2's 0400 key file also means any shell user can read the master key, so the 3-of-5 threshold is decoration. The honest claim would shrink to "root can read it", which is weaker than SR5 needs.

## (c) Concession
C2 is right that, in this build, the server combines shares in RAM for seconds regardless. Offline shares cut at-rest exposure but not operator trust, so we must say that. C2 is also right that pure offline (printed or typed pieces) fails H1's own rule against typing, and a lone tester cannot do it.

## (d) Compromise
- At sealing, each custodian's browser creates a non-extractable ECDSA P-256 key (WebCrypto, IndexedDB) and registers the public key. Their share is delivered once, wrapped under a **separate passphrase that never goes to the server**, and held by the custodian (browser storage plus a downloadable file). The server stores only the public key and a share hash.
- Release creates a request row (nonce, expiry 15 min, two-word check shown on the superintendent screen). The custodian's browser signs the request and sends the passphrase-unwrapped share inside that body. The server verifies the signature, the single use, the expiry and the check words, holds the share in RAM only, and discards it after combine or expiry. A replayed body fails; a stolen cookie without the key fails.
- Fallback: the threshold becomes 4 with a mandatory reason, an audit banner and a distinct route.
- **Lone tester:** a sandbox "Practice: you hold all five cards" button preloads five keystore slots in that browser. It is labelled, and not counted as security evidence. Attack tests run through the API with separate accounts. The honest claim is "three distinct keys and passphrases", not "three humans".
- **Cost:** about +1 day over C2's wrap design (0.5 for the sign/verify and request table, 0.5 for the client keystore and card UI), plus 0.25 for the fallback. Drop 4-of-5 to design-only if the day slips.

## (e) Biggest risk
The client keystore and signing flow eats 1.5 days and half-works on the VM. Even when it works, one XSS lets injected script use the non-extractable key, so SR10 becomes load-bearing. Mitigation: ship C2's wrapped storage with a separate passphrase plus the signed-request layer first, and move the keystore in only if the layer is finished by 14 Nov.
