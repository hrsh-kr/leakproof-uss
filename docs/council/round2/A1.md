# Q1, Advocate A1 (S1, pure pool-key design)

## (a) Strongest case
- **The claim is checkable.** "No plaintext exists on the VM at any time" can be tested by dumping the DB, process memory and logs after a full run. Under A2 the claim is "plaintext exists for seconds, trust us", and 8 classmates holding a shell or a heap snapshot will go for exactly those seconds.
- **The quorum guards the only exposure.** Under A1 the private key exists only in the centre tab after 3 custodians act. No single person (admin, operator, setter) can read a question at any earlier point.
- **Fewer ceremonies, not more.** A1 has one setup deal (admin's browser makes the keypair, deals 5 passphrase-locked shares) and one release. The draw runs on IDs by HMAC-stream, so there is no sealing event.

## (b) Two best attacks on A2 (D1+P2)
1. **A2 has no coherent answer to "who holds the pool private key at sealing?"** For the server to decrypt the 10 drawn questions, it must hold the pool private key or rebuild it from shares.
   - If it holds the key, the quorum is decorative: a DB-plus-process compromise reads all ~100 questions, not 10. "Only the drawn ones" is a policy, not a property.
   - If it rebuilds the key from shares, that is a third ceremony (setup, seal, release), which contradicts D1's "shares stored only wrapped to each custodian's public key".
   - P2's version is worse. It wraps each share under the custodian's scrypt-derived key, but the server receives the password at login to run scrypt. Unless the wrap passphrase is a separate secret that never touches the server, the server can unwrap every share and combine alone.
2. **Sealing is an ungated plaintext event.** The admin triggers the draw, so admin plus a VM operator read the paper with no quorum. The server also builds the paper and re-encrypts, so the plaintext paper sits in swap, core dumps and logs. It also breaks the guide's own claim that no single person can read before release.

## (c) Concession
A2 is right that A1's release rebuilds a key able to open all ~100 questions in the centre tab, not just 10. Cryptographically I cannot bound that. I can only bound it by policy: the server returns ciphertext for the drawn IDs only, and undrawn ciphertexts are deleted after release. I also concede that a malicious VM operator can serve altered JavaScript, so neither design defends against that. A1 still wins on the stolen-DB, passive-operator and heap-snapshot cases. A2 is also right that a tag-driven draw (topic balance) needs plaintext metadata, so I would keep that metadata as unencrypted tags.

## (d) Compromise I can live with
Build A1, with these cuts and fences:
- Use a vetted GF(256) Shamir library (pinned) over a 32-byte wrapping key.
- Use one fixed hybrid format: ECDH-P256 plus HKDF plus AES-GCM, with AAD `exam|q|setter|ver`.
- Use D1's ECDH relay for custodian-to-centre transfer, and drop the per-custodian public-key wrapping of stored shares.
- Add a sandbox-only "play all 5 custodians" button that visibly marks the ceremony as simulated, so a lone tester can finish it honestly.
- **Cut line at end of Day 2 morning:** if the end-to-end test (encrypt, draw IDs, 3 shares, release) is not green, fall back to trusted-draw server (C). In that case the server holds the key only in memory and the guide says so plainly.

Cost: about 1.5 days for A1, against about 1 day for A2. The extra half day buys the stronger claim. If the cut line triggers, the total is about 2 days, which is the fallback's price.

## (e) Biggest risk
The hybrid wrap/unwrap and share-transfer code is new, and it is written in the same days as auth and the UI. If we hit the cut line late, we ship C with a half-finished A1 in the repo, and testers read the code. The mitigation is to freeze the format and write test vectors on Day 1.
