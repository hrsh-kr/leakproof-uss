# A2 (D1 + P2): server seals in memory

## (a) Strongest case
- **Smallest ceremony load.** Only the release is a ceremony. A lone tester plays three custodians once. Sealing is one admin button. Nothing needs a quorum before questions exist.
- **Least new crypto.** The sealing path reuses `logic.mjs`: `seal`, `split`, wipe. We add a 256-bit Shamir and fix the RNG. S1 adds hybrid wrap and unwrap in three places (setter, private-key wrap under W, per-question unwrap), a third-party Shamir dependency and AAD formats. P2's own risk list says hand-rolled glue is where this build fails.
- **The release key covers only the paper.** The quorum rebuilds a fresh per-exam 256-bit key E, which opens the ~10 drawn questions. No human or browser ever holds a key that covers the whole pool. That is the exact question the brief raised, and S1 gets it wrong (see below).

## (b) Two best attacks on S1
1. **S1's release rebuilds the pool private key, which opens all ~100 questions in the centre tab.** Only server policy restricts which wrapped keys are sent. A compromised or XSS'd centre tab, or a server that is told to send everything, exposes the whole pool. That includes the questions for the next exam, since pools are reused. S1 lists this as a con and never fixes it. It also contradicts "the quorum opens only this exam."
2. **S1 has two ceremonies, not one, and its fallback is our design.** The private key must be generated and its shares dealt to five custodians before any question exists. That is a keygen-and-distribute ceremony with the dealer's browser holding the key. Then release is a second one. S1 also puts the pool key, W, a 3-of-5 library, PBKDF2 share blobs and per-question AAD into roughly 1.5 days. S1's own table names option C (trusted draw server) as the fallback. So S1 is A2 with extra risk.

## (c) Concession
S1 is right about two things. First, the claim "no plaintext on the server" is false in our design. The server sees the drawn ten for seconds, and a malicious VM operator sees them. Second, our round-1 text said the pool key was split "before any question exists" and also that the server decrypts at sealing. Those cannot both be true. Whoever decrypts at sealing holds the pool private key, so the VM operator can read the whole pool. We must state that plainly.

## (d) Compromise
Use S1's data format with A2's key custody.
- Each question gets a random AES-256 key, wrapped to a pool public key (WebCrypto RSA-OAEP, so setters cannot read each other's questions). The draw runs on question IDs and topic tags.
- The pool private key lives on the server, wrapped under a sealing key from a 0400 systemd credential. It is unwrapped only inside `seal()`, for the drawn ten, then zeroed.
- `seal()` builds the paper, encrypts it under a fresh 256-bit E, Shamir-splits E 3-of-5 and wipes E. Release rebuilds E only.
- The guide states the limit: a VM-root attacker reads the pool at sealing.
- Cost over the A2 baseline: about 0.5 day for the hybrid wrap and 0.25 day for 256-bit Shamir with duplicate and x=0 checks. Total about 1.5 days, against about 2.5-3 for S1.
- Because the question format is S1's, replacing the sealing key with a custodian quorum later is a custody change, not a data migration.

## (e) Biggest risk
Overclaiming. The sealing key sits on the same VM as the database, so one file-read bug (path traversal, `/proc/self/environ`, a backup that includes the credential) opens every pool question. A classmate who finds it takes the whole pool, which is worse than anything S1 allows. The mitigation is limited: scope the credential to the service user, exclude it from backups, and keep the claim to "a stolen database or backup alone holds nothing."
