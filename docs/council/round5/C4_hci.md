# C4: HCI / usable-security review of LeakProof (role-played), 14 Nov 2026

Sources read: course lectures 1, 3, 4, 7 and cheat sheet (HITL 6-question checklist section 1.10; gulfs of execution/evaluation, critical incident, key-task and "get it" testing, 3-5 users, pilot, metrics list, section 10), snapshot `public/app.js`, `index.html`, `USER_GUIDE.md`, `src/app.mjs`, `src/exam.mjs`, `scripts/official-setup.mjs`, `deploy/*`, Phase I report F1-F11, `11_minimal_system.md` section 3. Nothing was run in a browser; all UI claims come from reading code (marked "unverified in browser"). Whitten and Tygar's five properties do not appear in the lecture text I grepped (no "Whitten" hit); I use them from general knowledge and map them to the course's HITL checklist.

Short version: the flows are well built. The marks risk is in three things: (1) one-time secrets with no real guard against losing them, (2) a guide with an unfilled certificate step and several wrong or misleading sentences, (3) wording that promises something the UI does not do ("Set my own passphrase").

## 1. Cognitive walkthrough

Four questions per step: Q1 will the user try the right action, Q2 will they notice it, Q3 will they associate it with the goal, Q4 will they see progress. I list only steps where a question fails or a loss is possible; a step not listed passes all four. Times are my estimates for a first-time stranger (not measured).

### 0. Everyone: reach the site (guide section 1)
| Step | Issue |
|---|---|
| Open `https://192.168.2.238:8443/` | Self-signed cert: the browser shows a full-page warning. Guide only says "certificate fingerprint `<printed by install.sh>`" (placeholder, `USER_GUIDE.md` line 6) and never says what to click. Q1 fails for most strangers (gulf of execution). 1-3 min lost, some give up. Recovery: guide step with per-browser clicks. |
| Register (course code, username, display) | Code is a placeholder in the guide too. Username rule is shown in the form (good, `app.js` register). 1 min. |
| Secrets screen `secretsShown` | **Irrecoverable loss 1.** Passphrase and recovery code are generated by the server, shown once. Server has already stored them when the page appears (`/api/register` returns them). The "I have saved" checkbox only enables Continue; nothing stops closing the tab, reload, or ticking without saving. Reload keeps the session cookie, so the user is logged in for up to 30 min idle, then locked out for good (recovery code was on the same lost screen). Practice: register a new username (annoying, 3 min). Official: no operator reset route exists in `app.mjs` (I saw none), so a lost role means re-running setup. UI protection: warning text and checkbox only; no `beforeunload`, no forced Download, no re-display. |
| Log in later | Passphrase is `xxxx-xxxx-xxxx-xxxx` random base32 (`crypto.mjs` line 46). Typing 16 random characters from a downloaded file is slow and error-prone; "Show passphrase" helps. Paste works. |

### A. Setter submits a question
| Step | Result |
|---|---|
| Home, Open exam, tab "My questions" | Next-step box says "Add one question per topic" (`nextStep`). Q1-Q4 pass. |
| Choose topic, write question, 4 options, mark correct | Radio for "correct" is easy to miss: label is "Options (select the correct one)"; if skipped, error "Mark which option is correct (the round button)" appears (good recovery). Maxlength 500/200 enforced silently by the browser, no counter. |
| Submit | Toast "stored encrypted"; item appears with "(correct)". Delete needs second click within 4 s, else silently reverts (Q4 weak but harmless). |
Steps: about 8 actions, 2-3 min. Irrecoverable: delete of own question before sealing (guarded by two-step). In practice the setter role is one of the simplest tasks, but "one per topic" with 10 topics may puzzle a tester who wants to add several.

### B. Exam cell: seal, request release, print, trace (practice: same person)
| Step | Result |
|---|---|
| Seal | Button disabled until every topic ready; reason is beside it. Confirmation defaults focus to Cancel, Escape cancels, text says "cannot be undone" (good). Q2 weakness: after "Yes, seal it" it jumps to the cards tab (`refresh(x,'cards')`); a practice user is told to go there, fine. 3 actions, 30 s. **Irrecoverable by design.** Fully guarded. |
| Wait for cards verified | Cell tab shows "n of 5 verified". In practice the same user does it; Next-step box says so. |
| Request release | Seat count default 30; the button is disabled with the reason in plain text. Words appear on the cell screen only. Q3 risk: a practice tester has to remember two words while switching to the Key cards tab (the words live only on the cell tab). Usually fine (two short words). |
| Wait for approvals | Polls every 5 s; gate list with plain labels. Good. Request expires after 15 min (`RELEASE_TTL`): a slow first-time tester who has to load cards three times may expire it; recovery message is clear and the button "Request release again" is offered. |
| Print | Seat buttons open `#/copy/..` in a new tab; "Print" button. Seat count 30 with ×N reprint counters. Q4: printed state shown on the seat button. Fine. The log "reprint" is explained. |
| Trace | Needs 3 consecutive questions pasted from a copy. A stranger on a screen does not know what "consecutive" or "with options" means in practice; placeholder helps. Failure mode: user pastes only question text and gets "No seat has this order" and may read it as "the system is wrong". Recovery: result says how many questions were recognised. |
Total: about 12-15 minutes for a first run including cards (see section C), seal-to-print excluding cards about 4 min.

### C. Key holder: create, save, verify a card; approve
| Step | Result |
|---|---|
| Bulk "Create all my cards" (practice) | One passphrase twice, 10+ chars; reveal checkbox. PBKDF2 600k times 5 cards: "Working… (a few seconds)". Q1-Q4 pass. |
| Save file | Card text shown in a read-only textarea with Copy and Download. |
| **Verify** | **Irrecoverable loss 2.** Verify opens the card text and passphrase, then the server deletes its copy. The only thing verification proves is that the user can decrypt text that is still on screen or in the clipboard. It does not prove the file was saved to disk. A user can paste from the textarea, verify, close the tab, and the card is gone. The copy shown on screen is also not the same as "Load card file": the guide says "Download the file... Load it back", the UI offers either. Protection: explanatory sentence ("Save the card, then prove you can open it"), no enforcement. Before verification the loss is recoverable (`GET .../cards/:slot` is re-fetchable, as the design doc states), after it is not. Practice consequence: gate drops below 4, user must start a fresh exam (button on home). Official consequence: with 5 verified cards the quorum survives 2 lost; the stranger does not know that. |
| Reload or tab change while a card shows | `watchCards` checks for non-empty inputs/textareas and shows "Something changed... what you typed will be cleared" instead of wiping (good). The read-only card textarea counts as non-empty so it is protected from polling. A manual route change still destroys the screen; the card can be fetched again until verified. |
| Wrong passphrase at verify | "Wrong passphrase for card N, or the card text is damaged" (accurate; no hint on case or typo). Retry free. |
| Approve (three times in practice) | Per approval: type words, load file, type passphrase, press Approve. About 40 s each, 3 min for three. The words are typed identically each time, and a practice user holding all 5 cards approves their own request; the two-word check protects nothing in practice (same person, same screen). Guide should say so, otherwise a tester will "find" it. `RELEASE_ENDED.failed` after 5 wrong tries closes the request. |
| Refuse | Needs the words; closes for everyone. Fine and explained. |
Estimated practice key-card work: 5 min for creation, download, load and verify.

### D. Auditor checks the log
| Step | Result |
|---|---|
| Open public log | Link in "Log" tab and in the guide. Page is readable without login. Chain "Intact · N entries" with a green tick is clear. |
| Check a hash | Needs the 64-char hash from a copy footer. The footer shows "Log <hash>", full length, which must be selected and pasted, and the log head moves after each action (the printed head will be older than the chain head but still "in the chain"; the message "This hash is in the chain" is right). |
| Understanding | Phase I F3: the log was the least understood idea (44-57 percent clear). The page says "Tamper-evident log... chain" and nothing more (`logTab`). Q3 fails for non-technical users: "what do I do with the hash?" Needs one analogy sentence on the page. |
| Draw replay | One-line description pointing to `draw()` in source; a stranger cannot replay it without code. Acceptable for a scored security demo, not for a "usability" demonstration. |
Steps: 4 actions, 2 min if the hash is copied correctly.

### E. Lone practice tester doing everything
Minimum path: get past cert warning (1-3 min), register and save secrets (1.5 min), seal (0.5), create/verify cards (5), request release (0.5), approve three times (3), print one seat (0.5), trace (2), open log (1.5). About 15-18 minutes for a stranger with the guide. The 15-minute pilot slot is too short for all of it; cut to key tasks (section 3).
Two real hazards for a lone tester: the 15-minute release expiry, and the 10-practice-exam limit (429 message is plain).

## 2. Whitten and Tygar / HITL audit of security-critical interactions

Properties used: W&T (1) users are reliably made aware of the security tasks they must perform, (2) are able to figure out how, (3) do not make dangerous errors, (4) are sufficiently comfortable to continue using it. Plus the course 6-question HITL checklist (know, understand, know how, motivated, capable, will they actually do it).

| Interaction | Aware | Know how | No dangerous error | Comfortable | What we depend on; what happens if they do not |
|---|---|---|---|---|---|
| Card passphrase (self-chosen, 10+ chars, twice) | yes (Step 1 of 2) | yes | partial | partial | Depend on user remembering it and saving the file. No strength meter or "write it down" prompt. Weak or forgotten passphrase: card unusable after server copy is deleted. 10-char minimum is the only rule; "aaaaaaaaaa" passes (unverified in server but client check is length only, `checkNewPass`). Mitigation we have: survive 2 lost of 5. Capable and motivated? In a real exam a Dean who forgets the passphrase of a card used once a semester is the realistic failure. |
| Two-word check | yes | yes | yes | yes | Depends on the key holder being in the room. In practice it is theatre (same person); say so. Unusual human factor: words come from a 128-word list; fine. Social attack (read words over the phone) is not prevented; stated limit only. |
| Seal confirmation | yes | yes | yes (Cancel focused, Escape, text "cannot be undone") | yes | Best interaction in the app. If the user ignores it nothing bad happens beyond sealing early. Residual: seal does not show a summary of what will be drawn (counts only). |
| Recovery code (shown once, 12 base32 chars) | weak | yes | **no** | partial | Depends on the user saving it. Shown with the passphrase on one screen, so a single failed save loses both (same page). It is generated with the passphrase, not chosen. If they lose both: locked out; practice means re-register; official means the operator re-seeds (no route found). Recovery rotates the passphrase and recovery code, and shows both once again, so the same risk repeats. |
| Forced passphrase change (official accounts) | yes | **confusing** | partial | partial | Title is "Set your own passphrase" and the button says "Set my own passphrase" (`app.js` `passphrasePage`), but the user does not set anything: the server generates a new passphrase (`/api/passphrase` returns `passphrase`). The text then explains this. Gulf of evaluation: users expect a text box for a new passphrase and are surprised. A lost new secret is the same loss as the register screen. Also the "operator saw your first passphrase" explanation is honest and good. |
| Verify-then-delete of a card | yes | yes | **no** | yes | See loss 2. Depends on the user to download. No `Download` click is required. |
| "Show passphrase" | yes | yes | yes | yes | Good: addresses the typing burden of generated secrets. |
| Idle sign-out, 30 min | yes (flash) | yes | yes | partial | Good message and return to the same page. A lone tester busy in a think-aloud will hit it only if they stall; the guide mentions it. |
| Browser cert warning (outside the app) | **no** | **no** | **no** | no | Classic habituation problem. We ask users to click through a security warning to test a security tool. The guide should print the fingerprint and tell them what to compare; today it says `<printed by install.sh>`. The risk is also a marks risk: a classmate may file "self-signed certificate" as a vulnerability (known limit?) unless the guide states why and how to check it. |

Where we depend on the user to do the secure thing: keep the file and passphrase (cards), keep the login secrets, stay in the room for the words, compare the log head on the approval and cell screens (the UI says "should match" but no one is asked to act; if they do not, nothing breaks; the check has no enforcement). If they do not: irrecoverable card loss (bounded by 2 spare cards), irrecoverable account loss (no bound), nothing for the log-head comparison.

## 3. Usability testing evidence plan (Part A/B, video and poster)

Method (course vocabulary): key-task testing plus a short "get it" question, think-aloud on the first task only (Lecture 7: think-aloud slows users, so not on timed tasks), critical-incident log, post-task questionnaire. Pilot first, per the 8-step design process. 3 participants for the pilot (course says 3-4; Nielsen and Molich 4-5 is the exam-safe number: say pilot of 3, final of 5 if time allows).

Five tasks (each with a clear end criterion and 5-minute cap), all using only `USER_GUIDE.md`:
1. Get in: create account, save secrets. Success: reaches the Home page and has a downloaded or copied secrets file (check by asking them to log out and back in).
2. Seal the exam. Success: stage shows Sealed.
3. Create, save and verify key cards. Success: cards 1-5 verified and file on disk (check the Downloads folder: this catches loss 2).
4. Request release and approve with three cards. Success: paper opens.
5. Print seat 7 and trace a leak using three questions copied from it. Success: tool names seat 7.
(Optional 6, if time: auditor checks a hash from a copy footer in the log; this is the F3 concept.)

Metrics: completion with no help / with a hint / failed; time on task from screen record or the app's own log timestamps (below); error count (wrong passphrase, wrong card, wrong words, wrong tab); critical incidents (4-part report: problem, goal, intention, causes); help visits (count of times they open the guide); SUS (10 items) after the session, plus one Single Ease Question per task (1-7, same as Phase I ease ratings). UMUX-Lite (2 items) if there is no time for SUS; with 3 participants SUS is only descriptive, say so on the poster. Add one comprehension check per concept, as Phase I F2 taught us: "Why did the server delete the card?" and "What does the log prove?"; completion alone is a weak proxy.

15-minute pilot with 3 strangers on the VM, guide only:
- 0-2: consent and information sheet (design not participant is tested, can stop), no training, hand over the guide link only. 
- 2-12: tasks 1 to 4 (task 5 only if time); moderator silent, prompts "what are you thinking?" only when stuck; hint rule: one hint per task, recorded. Observers out of view if possible.
- 12-15: SUS or UMUX-Lite, two comprehension questions, open "worst moment". 
Likely over-run: tasks 1-3 alone take 8-10 min. Plan pilot tasks as 1, 3 and 4, and run 2 and 5 only in the full study.
- Reset between participants: unique username each, delete exam via fresh exam; clear cookies.
- Use unrelated people (not course-mates who have seen the app), since F2/F6 showed experts miss misunderstanding.

Instrumentation worth adding, ranked by risk: none in the app. Use the app's own public log for step timestamps (`GET /api/public/log/:id` returns `at` per event: seal, verify, release, print), plus a screen recording and a stopwatch. This adds zero code. Do not add client analytics before freeze: no tracking, no extra requests, no new failure modes, and any change to `app.js` after the last test run is a regression risk. If one thing is added, it is a "Download did not happen yet" nudge (see list), not telemetry.

## 4. User guide review (`USER_GUIDE.md`)

Missing steps:
- Certificate warning and fingerprint compare. Placeholders for fingerprint and course code (lines 5-6) must be filled before posting. Highest priority.
- No per-role credential table. The deliverable says "demo credentials for each role in our pipeline"; for practice there is only self-registration, so the table says "register yourself; you hold setter, exam cell and holders 1-5". For official: username per role (from `official.example.json`: setter-a, setter-b, examcell, controller, dean, registrar, hod, proctor) and "passphrase handed on paper, first login forces a change".
- No expected time, no browser or device note (Web Crypto and clipboard need current Chrome or Firefox; unverified on others), no "use two browser windows if you want to see the roles separately" (practice cannot show separation of duties).
- Release: no mention that the words are shown on the cell tab only, and that the request expires after 15 minutes (guide says it in passing as "expired"; it does not give the number).
- Check the record: says "paste the hash from a copy's footer" but never says that the copy footer shows the log head at print time, which will be older than the latest hash; the check still passes.

Wrong or misleading statements:
- "Release needs at least 4 verified cards, so one lost card is survivable" (section 2, Key cards 3): the gate is verification before release; survivable loss after full verification is 2 of 5. A classmate who loses two cards after verifying 5 and finds the exam still opens would file this as a guide bug. State both numbers precisely: "4 verified to request release; 3 must approve; after all 5 are verified you can lose 2".
- Section 1 step 4: "Change passphrase... then shows a new passphrase": correct. But the UI text says "Set my own passphrase"; make guide and UI agree (change UI, see list).
- "Optionally add your own under My questions (one per topic)": the practice exam has 10 topics and 4 simulated setters; the guide does not say that the exam already has every topic ready, so a tester wonders if they must submit anything. Say it is optional.
- "Four simulated setters have already written one question per topic": the seeding picks from a bank of 10 questions per topic (`seedPracticeExam`), fine, but the guide should say only 10 topics are used and that the draw is random.
- Section 3 "Idle sign-out after 30 minutes. The automatic refreshes do not keep you signed in": true by design (`X-LP-Background`); fine.
- Section 4 "Out of scope: the official instance (it is not running)": README says it is started on 25 Nov. State the date, otherwise the guide is false from 25 Nov.
- Section 4 mentions `SECURITY.md` section 4; the deployed testers may not have that file. Link or inline the known limits.

Jargon to replace: "log head", "chain", "quorum", "seat", "seal", "draw seed", "set hash". Phase I F6 says wording was the main usability problem (24 percent of comments). Add a six-line glossary.

Proposed structure:
1. What this is (3 sentences) and what you need (browser, 20 minutes, the address).
2. Before you start: certificate warning, fingerprint, course code.
3. Roles and credentials table (practice: you; official: username per role, how passwords reach you).
4. Task walkthroughs, one per role, each with: goal, steps (numbered, 5-9), "you know it worked when", "if it fails".
5. What to test, out of scope, known limits and works-as-designed (current section 3, one line each, linked to evidence).
6. How to report (what a valid report contains: steps, expected, actual, screenshot; where to send).
7. Glossary.
Every error in this document is a "functional bug" a classmate can file; run it once with a stranger before posting.

## 5. Ranked change list (smallest diff first)

Before freeze (17 Nov):
1. Fill fingerprint and course code in the guide; add the certificate-warning steps. Docs only. High impact, no code risk.
2. Fix the "4 verified, one lost card" sentence and the official-instance date in the guide. Docs only.
3. Rename the forced-change title and button in `passphrasePage` to "New passphrase" / "Get a new passphrase" (string change, 2 places; same string already used for the voluntary flow). Very low risk; removes a wording-vs-behaviour gap.
4. Add the per-role credentials table and "what to test / out of scope / known limits" section to the guide. Docs only.
5. In `secretsShown`: disable Continue until Copy or Download was clicked, or add a `beforeunload` guard while the screen is up. About 5 lines; moderate benefit; the risk is a bug in a screen every user passes. If done, test registration, recovery, forced change, and the official flow each once. Otherwise state the limit.
6. In `bulkCards` and `claimForm`: mark "Download" as done and show a warning on Verify if Download or Copy was never clicked. About 6 lines, one shared flag. Same risk class; weigh against freezing. This directly addresses irrecoverable loss 2.
7. Cut: nothing from the UI; do not add new screens, telemetry, or a glossary page to the app. Put the glossary in the guide.

State as a limitation instead of coding:
- Self-signed certificate: state why (offline VM) and how to verify the fingerprint.
- No operator reset for a lost official account: say it in the guide for the official demo.
- Log comprehension (F3), log-head comparison not enforced, two-word check meaningless for a solo tester, no passphrase strength meter, generated 16-character passphrases are hard to type (mitigated by Show and Paste).
- Not tested in Safari or on phones (Phase I F8: 51 percent of respondents used phones): the CSS has a viewport meta, but I did not run it; say "desktop Chrome and Firefox tested".

Honest reading: items 1-4 are worth doing today; items 5-6 are the only code changes with real marks value (they close the two irrecoverable-loss paths) and each is small. If the team has no appetite for any code change after the last green `npm test`, state both loss paths in the guide's "Known limits" and show them as lessons learnt in Part B.
